Understanding Spatial Hashing

By Trent Sterling • Feb 14, 2026 • Optimization Tutorial

Why your game lags at 1,000 units, and how a simple grid fixes it without allocating a single byte of garbage.

The Problem: The $O(N^2)$ Trap

You're building a game. You have 1,000 projectiles. You have 100 enemies. Every frame, you want to know if a projectile hit an enemy.

The naive way: foreach(projectile in bullets) foreach(enemy in enemies) CheckCollision(projectile, enemy);

That is 100,000 checks every single frame. At 2,000 bullets, it's 200,000. It's an exponential curve that kills your framerate.

"If you're checking every object against every other object, you're not writing a game; you're writing a benchmark."

The Solution: Spatial Partitioning

Instead of checking everything, we only check objects that are physically near each other.

A Spatial Hash is the simplest way to do this. You divide your world into a grid of cells (like a chessboard). Each object is "registered" into the cell it occupies.

When you want to find nearby objects, you only look at the cell you're in and its immediate neighbors.

CellX = floor(PosX / CellSize)
CellY = floor(PosY / CellSize)
CellZ = floor(PosZ / CellSize)

The "Hash" Part

Why is it called a hash? Because we take those 3D coordinates (X, Y, Z) and combine them into a single integer Key that we can use as a dictionary index. 

private int GetKey(Vector3 pos) {
    int x = Mathf.FloorToInt(pos.x / _cellSize);
    int y = Mathf.FloorToInt(pos.y / _cellSize);
    int z = Mathf.FloorToInt(pos.z / _cellSize);
    
    // Combine into a single unique integer
    unchecked {
        int hash = 17;
        hash = hash * 23 + x;
        hash = hash * 23 + y;
        hash = hash * 23 + z;
        return hash;
    }
}

How it avoids GC (Garbage Collection)

In Unity, memory allocation is the enemy. If you call new List<T>() every time you query the grid, you will create "Garbage" that the CPU has to clean up, causing "GC Spikes" (lag).

1. Pre-allocated Buffers

Don't let the function return a list. Instead, make the caller provide a list. 

// BAD: Allocates a new list every call
public List<T> Query(Vector3 pos) { 
    return new List<T>(); 
}

// GOOD: Fills an existing list (Zero Allocation)
public void Query(Vector3 pos, float radius, List<T> results) {
    results.Clear(); // Reuse the memory already in the list
    // Fill results...
}

2. Dictionary Buckets

We use a Dictionary<int, List<T>>. To avoid GC, we never "remove" the inner lists. We just clear them when the grid is empty. We also use TryGet to avoid throwing exceptions or creating new entries accidentally.

3. Managed vs. Native

While the code in this repo is "Managed" (C#), you can go a step further with Unity's Job System and NativeMultiHashMap. That moves the data to the "Native" side where the Garbage Collector can't even see it. For most games, the Managed pattern with pooled lists is 99% of what you need.

Real World Use Cases

1. Network AOI (Area of Interest)

Whether using PurrNet, FishNet, or Mirror, you only want to sync players who are close to each other.

The Server puts everyone in a Spatial Hash. Every tick, it queries a 50m radius around each player. It only sends position updates for the entities found in that query. This saves 90% of your bandwidth.

2. Pathfinding Node Lookup

Finding the "closest node" on a 5,000-node graph is slow. If you hash the nodes, you just query the cell the player clicked in. It's instant.

Summary

  • O(N²) is bad. Spatial hashing makes it close to O(1) or O(N).
  • The Grid is king. Simple division maps space to memory.
  • Reuse your lists. Don't new in the Update loop.
